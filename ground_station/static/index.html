Runtime Identifier Discovery & Acknowledgement Workflows

Standard operating procedures for discovering runtime entity IDs (events, faults, warnings), mapping values, and executing verifiable acknowledgements without guessing.

WORKFLOW 1: ACKNOWLEDGE EVENT

COMMAND 0x0A03 (2563)

event_id identifies either a static firmware event type (1..11 from nexus_event_queue.h) or a sequential event log ID from runtime queue snapshot.

Step 1: Discover Active Event IDs
curl -s http://127.0.0.1:8000/api/incidents | jq .firmware_event_types
Static Event Codes: 1=SYSTEM_BOOT, 2=JOB_STARTED, 3=JOB_COMPLETED, 4=JOB_FAILED, 5=DEADLINE_MISS, 6=QUEUE_OVERFLOW, 7=FAULT_LATCHED, 8=FAULT_CLEARED, 9=SENSOR_SAMPLE, 10=COMMAND_RECEIVED, 11=COMMAND_COMPLETED.
Step 2: Submit Valid Acknowledge Request
curl -X POST http://127.0.0.1:8000/api/command \ -H "Content-Type: application/json" \ -d '{"verb": "ACKNOWLEDGE", "noun": "EVENT", "params": {"event_id": 1}}'
Step 3: Expected Verification Response
{ "status": "ok", "code": 0, "msg": "Event acknowledged", "ack": true }

WORKFLOW 2: ACKNOWLEDGE FAULT

COMMAND 0x0A01 (2561)

fault_id identifies an active subsystem fault code (1=DHT Checksum Error, 2=Stale Telem, 3=Out of Bounds) or an incident record in Ground Station monitoring.

Step 1: Discover Active Faults
curl -s http://127.0.0.1:8000/api/incidents | jq '.active_incidents[] | select(.type=="FAULT")'
Step 2: Submit Valid Acknowledge Request
curl -X POST http://127.0.0.1:8000/api/command \ -H "Content-Type: application/json" \ -d '{"verb": "ACKNOWLEDGE", "noun": "FAULT", "params": {"fault_id": 1}}'
Step 3: Verification & Fault Reset
{ "status": "ok", "code": 0, "msg": "Fault acknowledged", "ack": true }
Note: To clear cumulative firmware error counters (jobs_failed = 0), submit CLEAR FAULTS with confirmation.

WORKFLOW 3: ACKNOWLEDGE WARNING

COMMAND 0x0A02 (2562)

warning_id identifies an active telemetry threshold alert (e.g., Code 2=Stale Telemetry, Code 3=Ultrasonic Range Exceeded, Code 5=Deadline Miss).

Step 1: Discover Active Warnings
curl -s http://127.0.0.1:8000/api/incidents | jq '.active_incidents[] | select(.type=="WARNING")'
Step 2: Submit Valid Acknowledge Request
curl -X POST http://127.0.0.1:8000/api/command \ -H "Content-Type: application/json" \ -d '{"verb": "ACKNOWLEDGE", "noun": "WARNING", "params": {"warning_id": 2}}'
Step 3: Verification Response
{ "status": "ok", "code": 0, "msg": "Warning acknowledged", "ack": true }

OPERATIONAL DISTINCTIONS: ACKNOWLEDGE vs CLEAR vs RESET

ACKNOWLEDGE (0x0A): Operator acknowledgment handshake. ESP32 logs the event transition and asserts ack: true. Does not reset monotonic counters or destroy historical evidence.
CLEAR FAULTS (0x0B01): Resets executive error counters (jobs_failed = 0) and unlocks safety latches. Requires operator confirmation.
RESET SYSTEM (0x04..): Destructive hardware or subsystem reset. Resets task queues and hardware peripherals.

Protocol Envelope Specification & Status Codes

Authoritative wire packet structure, execution routing targets, and response status codes.

CBOR & JSON ENVELOPE FORMAT

{ "ver": 1, // Protocol version (uint8) "dev": "nexus_esp32", // Device ID (string) "seq": 1024, // Monotonic sequence (uint32) "type": "cmd" | "resp" | ... // Packet type enum "cmd_id": 7938, // 16-bit command ID (uint16) "verb": "ASK", // Command Verb string "noun": "SENSOR", // Command Noun string "status": "ok", // Response status string "code": 0, // Integer StatusCode enum "msg": "AI response", // Human readable summary "params": {...}, // Parameter payload map "uptime_ms": 78200 // Monotonic uptime in ms }

EXECUTION TARGETS & TRANSPORTS

  • FIRMWARE (ESP32): Encoded in CBOR over active USB Serial (/dev/ttyUSB0 @ 115200) or MQTT (nexus/cmd). Dispatched by nexus_command_dispatcher.c.
  • GROUND_STATION: Executed locally on host Python server (HOST_LOCAL_OPERATION). No wire envelope is sent to ESP32. Includes ASK SENSOR, ASK SYSTEM, EXPORT TELEMETRY.
  • TEST_HARNESS: Simulated milestone verification commands routed to unit test mocks or host runner binary.
